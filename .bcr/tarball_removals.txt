# Files upstream's release tarball ships that the registry entry deletes, by a patch .github/scripts/export_bcr_entry.py
# generates from the tarball's own bytes and the list in the fork's .bcr/tarball_removals.txt: one path per line,
# sorted, each a non-empty text file the tarball ships and the fork does not commit.
#
# Specific to jemalloc 5.3.1's packaging: its release tarball was packed from a tree configure had already run in, so
# beside the release files it carries that machine's configured build tree. Of that tree, only the files at a path the
# Bazel build generates go: the configured headers under include/ and test/include/, where an unsandboxed compile finds
# the tarball's stale copy before the generated one, and public_symbols.txt. The rest (config.log, config.status, the
# empty config.stamp, Makefile, jemalloc.pc, bin/, doc/'s XML and XSL, test/test.sh and the private_symbols awk
# scripts) stays, like configure: nothing in the build generates or reads it. A branch for a release whose tarball is
# clean, such as 5.4.0, empties or removes this file.
